## Findings

### 1. [critical] Cancellation between controller success and journal completion leaves writes enabled
**Location**: `network/mcp-unifi/src/mcp_unifi/modules/_audit.py:206-221`
**Finding**: Once the wrapped tool returns, the success audit emit and `Authority.complete()` run outside the `try/except BaseException` that handles the tool body. If the MCP task is cancelled while `await log.emit(...)` is blocked, control exits before `authority.complete(operation, ...)`. The already committed attempt stays `pending`, but `Authority.healthy` remains true, so `/ready` can still report ready and a later granted write can proceed despite the required outcome record never being persisted.
**Evidence**: `Authority.begin()` commits the one-use grant and intent before controller I/O (`authority.py:194-223`). After the controller returns, `_audit.py:206` awaits the completion audit before `_audit.py:215-221` updates the durable attempt outcome. `AuditLog.emit()` can await its sink (`audit.py:276-280`); cancellation is a `BaseException`, so its `except Exception` does not absorb it. Since the outer success path has no cancellation cleanup, it neither marks the authority unhealthy nor blocks later writes. This violates the contract that failed outcome persistence makes readiness unhealthy and prevents subsequent writes.
**Suggestion**: Cover the post-mutation audit/completion phase with cancellation-safe cleanup. If completion cannot be durably recorded, mark the authority unhealthy and preserve/report an uncertain outcome before propagating cancellation. Add a synthetic test that blocks the completion sink, cancels after a successful mock mutation, then checks readiness and a subsequent write are refused.
